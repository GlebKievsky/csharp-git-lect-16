Главный закон: почему Git не страшный

Кажется, что одна неверная команда в Git уничтожит работу. На деле Git почти ничего не удаляет сразу.

Всё, что хоть раз было закоммичено, почти невозможно потерять. Хрупко только то, что ты ещё ни разу не закоммитил.

Закоммичено — спасаемо

Коммиты, даже «удалённые», продолжают храниться в папке .git. По умолчанию это не меньше 30 дней, и их можно найти (раздел 6).

Не закоммичено — хрупко

Изменения, которые ты ни разу не закоммитил и не спрятал в stash, Git просто не сохранял. Их вернуть нельзя.

Три вопроса перед любой отменой

  1. Где сейчас то, что я хочу отменить?Только в файлах? Уже добавлено через git add? Уже в коммите?
  2. Я уже сделал push?То есть есть ли это у других людей?
  3. Выбросить или отложить?Это больше не нужно — или нужно, но не сейчас?

Ответы на эти три вопроса однозначно выбирают команду. В разделе 8 они собраны в интерактивное дерево решений.

1

Что реально есть внутри Git

Чтобы отменять, нужно понимать, где лежат изменения. Здесь только настоящие файлы и папки, которые можно открыть и проверить.

Три места, где хранятся версии файлов

1. Рабочая папка (working directory)

Обычные файлы проекта на диске. Их ты видишь и редактируешь в редакторе.

2. Индекс (staging area)

Черновик следующего коммита. Физически это файл .git/index.

  • В индексе записано, какими будут все файлы в следующем коммите.
  • git add файл копирует текущую версию файла из рабочей папки в индекс.
  • Сразу после коммита индекс полностью совпадает с последним коммитом.

3. Репозиторий

База данных коммитов внутри папки .git. Коммит — это:

  • полный снимок всех отслеживаемых файлов;
  • автор, дата и сообщение;
  • ссылка на предыдущий коммит (родителя);
  • уникальный хэш, например 3f2a1bc.
Коммит нельзя изменить

Любое «исправление» коммита на самом деле создаёт новый коммит с новым хэшем.

Два указателя: ветка и HEAD

Ветка — это просто текстовый файл, в котором записан хэш одного коммита. Например, ветка main — это файл .git/refs/heads/main. Когда ты делаешь коммит, Git записывает в этот файл хэш нового коммита. Так ветка «растёт».

HEAD — файл .git/HEAD. В нём записано, на какой ветке ты сейчас находишься.

Проверь сам в любом репозитории:

cat .git/HEAD              # ref: refs/heads/main   ← ты на ветке main
cat .git/refs/heads/main   # 3f2a1bc9d8e7...        ← хэш последнего коммита main

В старых репозиториях ветки иногда хранятся в общем файле .git/packed-refs, но смысл тот же: ветка = имя + хэш.

Почему это важно для отмены

Почти каждая команда отмены делает одно из двух:

1Копирует версию файла

Из одного места в другое: коммит → индекс → рабочая папка.

2Переписывает хэш

В файле ветки: ветка начинает указывать на другой коммит.

Никакой магии, только эти две операции. Схема выше показывает их все.

Untracked-файлы

Untracked-файлы — это файлы в рабочей папке, которых нет ни в индексе, ни в последнем коммите. Например, новый файл, который ты ни разу не добавлял. Git о них ничего не знает. Поэтому restore и reset их не трогают, для них есть отдельная команда git clean.

git status сам подсказывает команды отмены

Строчки в скобках — готовые подсказки. Мало кто их читает, а зря:

On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        modified:   index.html

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
        modified:   style.css

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        notes.txt

Три блока означают три разные вещи:

  • Changes to be committed (зелёные) — индекс отличается от последнего коммита. Это попадёт в следующий коммит.
  • Changes not staged (красные) — рабочая папка отличается от индекса. Это ты изменил, но не добавил.
  • Untracked files — файлы, которых Git не знает.
Правило паники №1

Растерялся — набери git status и прочитай, что написано в скобках.

Как указывать на коммиты

  • HEAD — коммит, где ты сейчас.
  • HEAD~1 (или HEAD~) — его родитель, на один коммит назад.
  • HEAD~3 — на три коммита назад.
  • a1b2c3d — короткий хэш, первые 7 символов из git log --oneline.
  • HEAD^ тоже означает родителя, но в Windows (cmd) символ ^ особый, поэтому надёжнее ~.
2

Светофор опасности

Каждая команда в конспекте помечена цветом. Цвет говорит, можно ли потом отменить саму отмену.

Безопасно

Ничего не теряется.

  • git restore --staged
  • git reset --soft, git reset (mixed)
  • git revert, git stash
  • git commit --amendдо push
  • git merge --abort, git rebase --abort

Осторожно

Думай перед нажатием.

  • git reset --hardкоммиты вернёт reflog, а незакоммиченные правки — нет
  • git stash drop, git stash clearвернуть можно, но сложно
  • amend, reset, push --force после pushломают историю коллегам

Необратимо

Данные исчезнут навсегда.

  • git restore <файл>если в нём есть незакоммиченные правки
  • git clean -f
  • git reset --hardесли есть незакоммиченные изменения
Закон красного цвета

Всё красное уничтожает незакоммиченное. Git этих данных не сохранял, поэтому и вернуть не может. Перед красной командой сделай git stash или коммит, и она станет безопасной.

3

Отмена изменений: четыре ступени

Чем дальше ушло изменение, тем выше ступень и тем другой инструмент нужен. Нажми на ступень, чтобы перейти к ней.

  1. Ступень 1Просто изменил файлgit restore
  2. Ступень 2Сделал git addgit restore --staged
  3. Ступень 3Закоммитил, но не пушил--amend / reset
  4. Ступень 4Запушилgit revert
Отдельно: новые (untracked) файлыgit clean Отдельно: застрял посреди merge или rebase--abort
Ступень 1необратимо

git restore <файл>Вернуть файл

Ситуация. Наредактировал файл, всё сломал и хочешь вернуть как было. git add ещё не делал.

git diff style.css        # сначала посмотри, ЧТО именно сотрёшь
git restore style.css     # вернуть один файл
git restore .             # вернуть все изменённые файлы в текущей папке

Что происходит. Git берёт версию файла из индекса и записывает её поверх файла в рабочей папке. Если ты не делал git add, в индексе лежит версия из последнего коммита, к ней файл и вернётся.

Опасность

Правки исчезают навсегда. Они не попадают ни в корзину, ни в reflog. Если файл ещё открыт в редакторе, иногда спасает Ctrl+Z.

Нюансы

  • Новые (untracked) файлы restore не трогает.
  • Если ты сделал add, а потом поменял файл ещё раз, git restore файл вернёт его к версии из индекса, а не из коммита.
  • Чтобы вернуть файл сразу к последнему коммиту и в индексе, и в рабочей папке: git restore -SW файл (сокращение от --staged --worktree).

Старый синтаксис из статей: git checkout -- style.css

Ступень 2безопасно

git restore --staged <файл>Убрать из индекса

Ситуация. Сделал git add ., а туда попал лишний файл (debug.log, config.local).

git restore --staged debug.log   # убрать один файл из индекса
git restore --staged .           # убрать из индекса всё

Что происходит. Git записывает в индекс версию файла из последнего коммита. Рабочая папка не меняется, твои правки остаются на месте. Файл просто перестаёт быть «подготовленным к коммиту».

Совет

Если файл вообще никогда не должен попадать в коммит, добавь его в .gitignore.

Как запомнить

restore без флага меняет рабочую папку, с флагом --staged меняет индекс. Флаг прямо называет, какое место меняем.

Старый синтаксис: git reset HEAD debug.log или просто git reset debug.log

Ступень 3безопасно до push

git commit --amendИсправить последний коммит

Ситуация 1. Опечатка в сообщении последнего коммита.

git commit --amend -m "Исправленное сообщение"

Ситуация 2. Забыл добавить файл в последний коммит.

git add forgotten.js
git commit --amend --no-edit     # --no-edit: сообщение оставить прежним

Что происходит. Коммит нельзя изменить, поэтому Git создаёт новый коммит:

  • его содержимое берётся из текущего индекса;
  • его родитель — тот же, что у старого коммита;
  • его хэш записывается в файл ветки.

Старый коммит не удаляется. Он просто больше не входит в ветку, а reflog его помнит.

Ограничения

Только последний коммит и только если ты его ещё не пушил. Иначе твоя история разойдётся с серверной (раздел 4).

Ступень 3--soft, --mixed--hard

git resetПеренести ветку назад

Это главная и самая пугающая команда. На самом деле она устроена просто.

git reset <коммит> выполняет до трёх шагов по порядку:

  1. Записывает хэш указанного коммита в файл текущей ветки. Ветка теперь указывает на более старый коммит. Все режимы делают этот шаг.
  2. Копирует содержимое этого коммита в индекс. Этот шаг делают --mixed и --hard.
  3. Копирует содержимое этого коммита в рабочую папку. Этот шаг делает только --hard.

--soft останавливается после шага 1, --mixed — после шага 2, --hard делает все три.

Мнемоника «1-2-3»

soft меняет одно место (ветку), mixed — два (ветку и индекс), hard — все три.

Практические рецепты


# 1. Отменить последний коммит, но сохранить изменения
git reset --soft HEAD~1

# 2. Склеить последние 3 коммита в один (частая задача перед push!)
git reset --soft HEAD~3
git commit -m "Одно понятное сообщение вместо трёх"

# 3. Выбросить ВСЕ незакоммиченные правки в отслеживаемых файлах
git reset --hard

# 4. Сделать свою ветку точно как на сервере
git fetch
git reset --hard origin/main

# 5. Отменить неудачный merge или rebase (до push)
git reset --hard ORIG_HEAD

    
Рецепт 3 — необратимо, рецепты 4 и 5 — осторожно.

    
Что такое ORIG_HEAD. Перед merge, rebase и reset Git записывает хэш текущего коммита в файл .git/ORIG_HEAD. Поэтому git reset --hard ORIG_HEAD возвращает всё к состоянию до последней такой операции.

    

      
      Не путай
      
git reset <файл> с указанием файла ветку не двигает. Он только копирует версию файла из коммита в индекс, то же самое, что git restore --staged.

    

    

      
      Главное предупреждение
      
reset меняет историю ветки, поэтому применяй его только к коммитам, которые ещё не пушил.

    

    

      
      Страховка перед --hard
      
Сделай git branch backup (ещё одна ветка на текущий коммит) или git stash (сохранить незакоммиченное). Тогда даже --hard станет обратимым.

    

  


  
  

    
Ступень 4безопасно

    
git revertОтменить запушенный коммит

    
Ситуация. Плохой коммит уже запушен, коллеги его скачали.

    
Почему нельзя reset. У коллег этот коммит уже есть, и их новые коммиты могут на нём основываться. Если убрать его у себя через reset, будет вот что:

    
    
      
  • твоя история перестанет совпадать с серверной;
    • 
      
  • обычный push отклонят, придётся делать push --force;
    • 
      
  • force перезапишет ветку на сервере;
    • 
      
  • у коллег история разойдётся с серверной, а при неосторожном force можно затереть чужие запушенные коммиты.
    • 
    

    
Решение. Ничего не удалять, а создать новый коммит, который делает ровно обратное плохому. Строки, которые плохой коммит добавил, новый удаляет, и наоборот. История при этом только растёт.

    

git revert HEAD                      # отменить последний коммит
git revert a1b2c3d                   # отменить любой коммит, даже глубоко в истории
git revert a1b2c3d --no-edit         # не открывать редактор сообщения
git revert HEAD~3..HEAD              # отменить три последних (три revert-коммита)
git revert --no-commit HEAD~3..HEAD  # то же одним коммитом (потом git commit)
git revert -m 1 <хэш-merge>          # отменить merge-коммит

    
Детали

    
    
      
  • Конфликт при revert возможен, если после плохого коммита кто-то менял те же строки. Решаешь его как при merge, затем git add и git revert --continue. Или всё отменяешь через git revert --abort.
    • 
      
  • Отмену можно отменить: git revert на revert-коммит вернёт изменения обратно.
    • 
      
  • Если открылся редактор Vim, набери :wq и нажми Enter. Или сразу используй --no-edit.
    • 
    

    

      
      Как запомнить
      
reset убирает коммиты из истории, revert добавляет в историю коммит-отмену.

    

  


  
  

    
Отдельнонеобратимо

    
git cleanУдалить untracked-файлы

    
restore и reset работают только с файлами, которые Git отслеживает. Новые файлы (логи, результаты сборки, случайные черновики) они не трогают. Для них есть clean.


git clean -n        # ПРОСМОТР: показать, что будет удалено (ничего не удаляет)
git clean -f        # удалить untracked-файлы
git clean -fd       # + untracked-папки
git clean -i        # интерактивно: спросит про каждый файл
git clean -fdx      # + файлы из .gitignore (node_modules, .env!) — очень осторожно

    

      
      Опасность
      
Файлы удаляются с диска мимо корзины. Флаг -x удалит даже твой .env с паролями.

    

    

      
      Правило
      
Всегда сначала -n (от «dry run», пробный прогон).

    

  


  
  

    
Отдельнобезопасно

    
--abortВыйти из merge и rebase

    
Если посреди merge или rebase посыпались конфликты и хочется вернуться к состоянию до начала:


git merge --abort
git rebase --abort
git cherry-pick --abort
git revert --abort

    

      
      Совет
      
Начинай merge и rebase с чистым git status, тогда --abort отработает без сюрпризов.

Золотое правило: reset или revert

      
Всё решает один вопрос: видел ли кто-то ещё эти коммиты.

    

  


  

    

      
Не пушил

      
Можно reset и amend: меняй свою историю как хочешь.

    

    

      
Запушил

      
Только revert: историю, которая есть у других, не переписываем.

    

  


  

    

      
git resetgit revert

      
        
Что делаетПереносит ветку на старый коммитДобавляет новый коммит с обратными изменениями

След в историиНетЕсть («Revert …»)

        
После pushОпасно, нужен force pushБезопасно

reSet — для Себя

      
Переписывает историю. Годится, пока коммиты есть только у тебя.

    

    

      
reVert — для Всех

      
Только добавляет коммит. Безопасно для общей истории на сервере.

    

  


  

    
    Исключение
    
Если это твоя личная ветка на сервере и в ней никто больше не работает, можно переписать историю (amend, reset, rebase) и отправить её через git push --force-with-lease. Этот вариант force откажется перезаписывать ветку, если на сервере появились чужие коммиты.

  







  

    5
    

      
Архивация: git stash

      
Как отложить незаконченную работу, не делая коммит, и потом вернуть её.

    

  


  
Зачем

  
Ты делаешь фичу, полфайла написано, код даже не запускается. И тут: «Срочно почини баг на main!» Коммитить незаконченное не хочется, а переключить ветку Git не даёт:


error: Your local changes to the following files would be overwritten by checkout:
        app.js
Please commit your changes or stash them before you switch branches.

  
Git сам подсказывает: «or stash them».


  

    
Что stash делает на самом деле

    
    
      
  1. Берёт все незакоммиченные изменения отслеживаемых файлов: и из индекса, и из рабочей папки.
    2. 
      
  2. Сохраняет их в специальный коммит, который не принадлежит ни одной ветке. Ссылка на него хранится в .git/refs/stash.
    3. 
      
  3. Возвращает индекс и рабочую папку к последнему коммиту. После этого git status чистый.
    4. 
    

    
Потом эти изменения можно применить обратно на любой ветке.

  


  

    
Базовый цикл


git stash -u -m "форма логина, недоделано"   # спрятать
git switch main                              # переключиться
# ... чиним баг, коммитим ...
git switch feature                           # вернуться
git stash pop                                # достать обратно

  


  

    
Список стэшей — это стопка

    
Новая запись добавляется сверху и получает номер 0, а номера остальных увеличиваются на 1:


$ git stash list
stash@{0}: On feature: форма логина, недоделано        ← самый свежий
stash@{1}: WIP on feature: 3f2a1bc Add header
stash@{2}: On main: эксперимент с цветами

    

      
      Номера меняются
      
После каждого pop, drop и нового stash. Перед работой с конкретным номером смотри git stash list. Попробуй в тренажёре: удали запись из середины и посмотри, как сдвинутся номера.

    


    

      

        
Тренажёр: stash нажимай команды

        
      

      

        
Кликни по записи в списке, чтобы выбрать её номер. Команды apply, pop и drop работают с выбранной записью.

        

          
          
          
          
          
        

        
$git stash list

    Рабочая папка
    
            
    
          
    
        
    
        
    
      
    
    
    
  
    

  
    
    
    Все команды
    
    
    
      
    
        
    КомандаЧто делает
    
        
          
    git stash
    = git stash push    		Спрятать изменения отслеживаемых файлов
    
          
    git stash push -m "текст"То же, с подписью
    
          
    git stash -uСпрятать ещё и untracked-файлы (u = untracked)
    
          
    git stash -aСпрятать даже игнорируемые файлы (a = all)
    
          
    git stash listПоказать список
    
          
    git stash show -p stash@{1}Показать содержимое в виде diff (p = patch)
    
          
    git stash apply stash@{1}Применить изменения, запись остаётся в списке
    
          
    git stash drop stash@{1}Удалить запись осторожно
    
          
    git stash popПрименить верхнюю запись и удалить её
    
          
    git stash clearУдалить все записи осторожно
    
          
    git stash branch имяСоздать ветку и применить стэш в ней
    
            
      
    
    
    
    
    
      
      Главная формула
      
    pop = apply + drop
    
    
    
  
    

  
    
    
    Пять ловушек
    
    
    
      
    Новые файлы без -u не прячутся. Классика: сделал git stash, переключил ветку, а новый файл остался в папке. Он untracked, Git его не трогал. Правило: сомневаешься — прячь с -u.
    
      
    Подписывай стэши (-m). Через неделю надпись «WIP on feature» ничего тебе не скажет.
    
      
    Конфликт при pop. Если после stash ты менял те же строки, будет конфликт, решаешь как обычно. При конфликте pop не удаляет запись из списка, чтобы ничего не потерялось. После решения удали её сам: git stash drop.
    
      
    Индекс не восстанавливается. pop и apply по умолчанию возвращают изменения, но не восстанавливают, какие из них были в индексе. Если это важно: git stash pop --index.
    
      
    Stash — не склад. Он хранится только на твоём компьютере и не пушится. Для долгого хранения делай коммит в отдельную ветку.
    
    
    
  
    

  
    
    
    Продвинутое
    

    git stash push -m "только стили" -- style.css   # спрятать конкретные файлы
git stash -p                                    # выбрать части изменений интерактивно
git stash --staged                              # спрятать только то, что в индексе (Git 2.35+)
git stash --keep-index                          # спрятать всё, но индекс оставить как есть
git stash branch fix-later stash@{0}            # стэш не применяется из-за конфликтов?
                                                # создаст ветку от коммита, на котором
                                                # стэш был сделан, и применит его там
git pull --autostash                            # сам спрячет и вернёт правки вокруг pull
    
    
    
      
      Для Windows PowerShell
      
    Фигурные скобки там особые, поэтому пиши git stash apply "stash@{1}" в кавычках. Или короче: git stash apply 1, ведь просто номер тоже работает.
    
    
    
  
    

  
    
    
    Альтернатива stash: временный коммит
    

    git add -A && git commit -m "WIP"   # сохранить черновик обычным коммитом
# ... переключился, поработал, вернулся ...
git reset HEAD~1                    # убрать коммит: изменения снова в рабочей папке

    Спасение: git reflog
    
      
    Команда, после которой Git перестаёт пугать. Она находит коммиты, которые «пропали».
    
    
    
  
    

  
    Ситуация
    
  
    Ты сделал git reset --hard HEAD~3. Три коммита пропали, git log их не показывает.
    

  
    
    
    Почему log их не видит
    
    
    git log идёт от текущего коммита назад по ссылкам на родителей и показывает эту цепочку. Ветка теперь указывает на более старый коммит. Отрезанные коммиты в цепочку от него не входят, поэтому log их не видит. Но сами коммиты по-прежнему хранятся в .git.
    
    
    git reflog — это отдельный журнал. Физически это файл .git/logs/HEAD. Каждый раз, когда HEAD меняется, Git дописывает туда строку: какой коммит был, какой стал и какой командой. Это происходит при commit, switch/checkout, reset, merge, rebase, amend, pull и cherry-pick. У каждой ветки есть свой такой журнал: .git/logs/refs/heads/main.
    
    
    
      
    
        
    git log
    
        
    История коммитов. Идёт по родителям.
    
        
      
          
    1. 3f2a1bcCommit 1
      2. 
          
    2. Три отрезанных коммита сюда не попадают
      3. 
        
    
      
    
      
    
        
    git reflog
    
        
    История твоих действий. Помнит всё.
    
        
      
          
    1. 3f2a1bcreset: moving to HEAD~3
      2. 
          
    2. 9d8e7f6commit: Добавил валидацию формы
      3. 
          
    3. 5c4b3a2commit: Сделал форму логина
      4. 
          
    4. 1a2b3c4commit: Добавил стили
      5. 
        
    
      
    
    
    
    
    Итог: git log показывает историю коммитов, git reflog показывает историю твоих действий.
    
  
    

  
    
    
    Как читать reflog
    

    $ git reflog
3f2a1bc (HEAD -> main) HEAD@{0}: reset: moving to HEAD~3
9d8e7f6 HEAD@{1}: commit: Добавил валидацию формы
5c4b3a2 HEAD@{2}: commit: Сделал форму логина
1a2b3c4 HEAD@{3}: commit: Добавил стили
3f2a1bc HEAD@{4}: checkout: moving from feature to main
    
    
      
      
    • HEAD@{0} — где HEAD сейчас.
      • 
      
    • HEAD@{1} — где HEAD был одно действие назад. HEAD@{2} — два действия назад, и так далее.
      • 
    
    

    
    
      
    
        
    HEAD~1
    
        
    Родитель текущего коммита. Шаг назад по истории.
    
      
    
      
    
        
    HEAD@{1}
    
        
    Где был HEAD до последнего действия. Шаг назад по журналу reflog.
    
      
    
    
    
    
    Это важнейшее различие и частый вопрос на собеседованиях. Проверь себя в тренажёре:
    

    
    
      
    
        
    Тренажёр: куда указывает ссылка
    
        
    
          
          
          
          
        
    
      
    
      
    
        
    Ты сделал коммиты A, B, C, D, а потом выполнил git reset --hard HEAD~2. Теперь ветка main указывает на B.
    
        
    
          
          
          
          A
          B
          C
          D
          mainHEAD
        
    
        
    Выбери ссылку вверху справа.
    
      
    
    
    
  
    

  
    
    
    Спасение
    

    git show 9d8e7f6               # сначала убедись, что это нужный коммит
git reset --hard HEAD@{1}      # вернуть ветку туда, где она была до reset
# или самый безопасный вариант: ничего не трогать, создать ветку на этот коммит
git branch rescue 9d8e7f6
    
  
    

  
    
    
    Пять сценариев спасения
    
    
    
      1После reset --hard
      
    Так, как показано выше: находишь в reflog строку до reset и возвращаешься на неё через git reset --hard HEAD@{n} или создаёшь ветку git branch rescue <хэш>.
    
    
    
    
    
      2Удалил ветку
      
    
        
    Удаление ветки — это удаление файла с хэшем. Сами коммиты остаются. Git при удалении печатает этот хэш:
    

    Deleted branch feature (was 7e6d5c4).
    
        
    Восстановление — создать файл ветки заново: git branch feature 7e6d5c4.
    
        
    Если сообщение уже потерялось, ищи в reflog запись checkout: moving from feature to .... Строчка под ней (более старая) — последний коммит ветки feature.
    
      
    
    
    
    
    
      3Неудачный rebase
      
    
        
    Сразу после rebase поможет git reset --hard ORIG_HEAD. Если после этого ты уже что-то делал, найди в reflog строку rebase (start). Запись под ней — состояние до rebase:
    

    git reset --hard HEAD@{5}      # номер строки, которая идёт перед rebase (start)
    
      
    
    
    
    
    
      4Отменить amend
      
    

    git reset --soft HEAD@{1}      # ветка вернётся к старому коммиту,
                               # а добавленное через amend окажется в индексе
    
      
    
    
    
    
    
      5Коммиты вне веток (detached HEAD)
      
    Если сделать git checkout a1b2c3d, в .git/HEAD записывается хэш коммита, а не имя ветки. Новые коммиты в таком состоянии не попадают ни в одну ветку. Когда ты переключишься на main, на них ничего не будет указывать. Находишь их хэш в reflog и делаешь git branch saved <хэш>.
    
    
    
  
    

  
    
    
    Время вместо номеров
    

    git reflog --date=relative     # показать «2 hours ago» вместо номеров
git show main@{yesterday}      # на какой коммит указывал main вчера
git diff HEAD@{1.hour.ago}     # что изменилось за последний час
    
  
    

  
    
    
    Ограничения
    
    
      
      
    • reflog локальный. На другом компьютере и в свежем клоне его нет, push его не отправляет.
      • 
      
    • У записей есть срок годности. По умолчанию записи хранятся около 90 дней. Для коммитов, которые не входят ни в одну ветку, — около 30 дней. Потом очистка (git gc) может удалить и записи, и сами коммиты.
      • 
      
    • reflog знает только о коммитах. Правки, стёртые через restore, reset --hard или clean до коммита, он не спасёт. Это снова главный закон.
      • 
    
    
  
    

  
    
    
    Спасение удалённого стэша
    
    
    Для продвинутых.
    
    
    При pop и drop Git печатает строку вида Dropped refs/stash@{0} (6f3e2a1…). Скопируй хэш и выполни git stash apply 6f3e2a1. Если терминал уже закрыт:
    

    git fsck --no-reflog | grep "dangling commit"   # коммиты, на которые ничего не указывает
git show <хэш>                                  # ищешь среди них свой стэш

    Бонус: git archive
    
      
    Архивация в прямом смысле: упаковать файлы проекта в zip или tar.
    
    
    
  
    

    git archive --format=zip -o project.zip HEAD                        # текущий коммит
git archive --format=zip -o release-v1.0.zip v1.0                   # по тегу
git archive --format=tar.gz --prefix=myapp/ -o myapp.tar.gz main    # tar.gz с папкой внутри

    • Только файлы из выбранного коммита
    
    
    
    
    
      
    Не попадает
    
      
    • Папка .git
    • node_modules, логи и прочие неотслеживаемые файлы
    • Незакоммиченные правки
    
    
    
  
    
  
    Когда полезно: сдать лабу преподавателю, отправить код заказчику, собрать релиз. Это надёжнее, чем архивировать папку проекта вручную.

    Рецепты «Я хочу…» и дерево решений
    
      
    Ответь на пару вопросов, и дерево назовёт нужную команду.
    
    
    
  
    

  
    
    
    
      
    Что я хочу отменить? дерево решений
    
    
    
    
    
  
    

  
    
    Показать всё дерево целиком

    Что я хочу отменить?
│
├── Правки, которые ещё НЕ закоммичены
│     ├── выбросить навсегда ............. git restore <файл>          [необратимо]
│     │                                    (новые файлы: git clean -n → -f)
│     ├── убрать из индекса .............. git restore --staged <файл> [безопасно]
│     └── отложить на потом .............. git stash -u                 [безопасно]
│
└── Коммиты
      ├── ещё НЕ запушены
      │     ├── исправить последний ...... git commit --amend           [безопасно]
      │     └── убрать последние N ....... git reset --soft / --mixed / --hard HEAD~N
      ├── УЖЕ запушены ................... git revert <хэш>             [безопасно]
      └── «пропали» после моих действий .. git reflog                   [безопасно]
    
  
    

  
    
    
    Рецепты
    
    
    
    
      
    
        
    СитуацияКомандаОпасность
    
        
          
    Испортил файл, add не делалgit restore файл
    
          
    Добавил лишний файл в индексgit restore --staged файл
    
          
    Выбросить вообще все незакоммиченные правкиgit reset --hard (+ git clean -fd для новых файлов)
    
          
    Опечатка в сообщении последнего коммитаgit commit --amend -m "…"
    
          
    Забыл файл в последнем коммитеgit add файл → git commit --amend --no-edit
    
          
    Отменить последний коммит, сохранив измененияgit reset --soft HEAD~1
    
          
    Склеить N последних коммитовgit reset --soft HEAD~N → git commit
    
          
    Удалить последний коммит полностью (не пушил)git reset --hard HEAD~1
    
          
    Отменить запушенный коммитgit revert хэш
    
          
    Начал работу не в той ветке (ещё не коммитил)git switch -c нужная-ветка (незакоммиченные правки останутся в папке)
    
          
    Закоммитил в main вместо новой ветки (не пушил)git branch feature → git reset --hard HEAD~1 → git switch feature
    
          
    Срочно переключиться, работа не готоваgit stash -u → … → git stash pop
    
          
    Застрял в конфликте merge или rebasegit merge --abort / git rebase --abort
    
          
    Merge или rebase прошёл, но результат плохой (не пушил)git reset --hard ORIG_HEAD
    
          
    Запушенный merge оказался плохимgit revert -m 1 хэш-merge
    
          
    «Потерял» коммиты после reset или rebasegit reflog → git reset --hard HEAD@{n} или git branch rescue хэш
    
          
    Удалил веткуgit branch имя хэш
    
          
    Удалить новые мусорные файлыgit clean -n → git clean -fd
    
          
    Вернуть файл к версии из старого коммитаgit restore --source=хэш файл
    
          
    Сделать ветку точно как на сервереgit fetch → git reset --hard origin/main
    
          
    Сдать проект архивомgit archive --format=zip -o project.zip HEAD
    
          
    Ничего не найдено. Попробуй другое слово, например «коммит» или «файл».
    
            
      
    
    
    
    
     безопасно    осторожно    необратимо

    Старые и новые команды
    
      
    Словарик для чтения старых статей и ответов на Stack Overflow.
    
    
    
  
    
  
    В Git 2.23 (2019 год) команду checkout, которая делала слишком много разного, разделили на две: switch для веток и restore для файлов.
    
  
    
    
    
      
    Старая командаНовый аналог
    
      
        
    git checkout -- файлgit restore файл
    
        
    git reset HEAD файлgit restore --staged файл
    
        
    git checkout веткаgit switch ветка
    
        
    git checkout -b новаяgit switch -c новая
    
        
    git checkout хэш -- файлgit restore --source=хэш -SW файл
    
        
    git stash save "текст"git stash push -m "текст"

    Практикум «Сломай и почини»
    
      
    Лучший способ перестать бояться — самому сломать и починить. Создай учебный репозиторий и делай всё по шагам.
    
    
    
  
    
  
    Команды рассчитаны на Git Bash (Windows), терминал macOS или Linux. Основная ветка может называться main или master: смотри вывод git branch и подставляй своё имя. Отмечай выполненные упражнения, отметки сохранятся в этом браузере.

    ПодготовкаСоздать песочницу
    

    mkdir git-sandbox && cd git-sandbox
git init
echo "line 1" > app.txt
git add app.txt && git commit -m "Commit 1"
echo "line 2" >> app.txt && git commit -am "Commit 2"
echo "line 3" >> app.txt && git commit -am "Commit 3"
git log --oneline
cat .git/HEAD                 # на какой ты ветке
cat .git/refs/heads/main      # хэш последнего коммита — сравни с git log
    
  
    

  
    
    
    Упражнение 1Откатить изменения в файле
    

    echo "garbage" >> app.txt
git status               # app.txt красный — modified
git diff                 # видно, что добавилось
git restore app.txt
cat app.txt              # garbage исчез
    
  
    

  
    
    
    Упражнение 2Убрать файл из индекса и удалить untracked-файл
    

    echo "password=123" > secret.txt
git add .
git status               # secret.txt зелёный — в индексе
git restore --staged secret.txt
git status               # снова untracked
git clean -n             # Would remove secret.txt
git clean -f
    
  
    

  
    
    
    Упражнение 3Исправить последний коммит
    

    git log --oneline        # запомни хэш последнего коммита
git commit --amend -m "Commit 3 (fixed)"
git log --oneline        # хэш другой — это новый коммит
    
  
    

  
    
    
    Упражнение 4Три режима reset
    

    cat .git/refs/heads/main          # хэш до reset
git reset --soft HEAD~1
cat .git/refs/heads/main          # хэш изменился — ветка перенесена
git status                        # изменения зелёные (в индексе)
git commit -m "Commit 3 again"

git reset HEAD~1
git status                        # изменения красные (в рабочей папке)
git commit -am "Commit 3 again"

git reset --hard HEAD~1
git status                        # чисто
git log --oneline                 # коммита 3 нет. Переходи к упражнению 5
    
  
    

  
    
    
    Упражнение 5 — самое важноеВернуть коммит через reflog
    

    git reflog               # в HEAD@{1} видно "commit: Commit 3 again"
git reset --hard HEAD@{1}
git log --oneline        # коммит вернулся
cat app.txt              # line 3 на месте
    
    
    
      
      
    Только что ты «удалил» коммит и вернул его. После этого упражнения reset перестаёт пугать.
    
    
    
  
    

  
    
    
    Упражнение 6Восстановить удалённую ветку
    

    git switch -c experiment
echo "experiment" >> app.txt && git commit -am "Experiment"
git switch main
git branch -D experiment          # Deleted branch experiment (was 1a2b3c4).
git branch experiment 1a2b3c4     # подставь свой хэш
git log experiment --oneline      # ветка на месте
    
  
    

  
    
    
    Упражнение 7Stash
    

    echo "half-done feature" >> app.txt
echo "new file" > todo.txt
git stash
git status               # app.txt спрятан, а todo.txt остался (untracked)
git stash pop

git stash -u -m "feature in progress"
git status               # теперь чисто
git stash list
git switch -c hotfix
echo "fix" >> app.txt && git commit -am "Hotfix"
git switch main
git stash pop            # изменения вернулись
    
  
    

  
    
    
    Упражнение 8Revert
    

    git add . && git commit -m "Feature"
git revert HEAD --no-edit
git log --oneline        # появился коммит Revert "Feature"
git revert HEAD --no-edit   # отменили отмену — изменения вернулись

    Вопросы для самопроверки
    
      
    Сначала ответь сам, потом открой ответ.
    
    
    
  
    
  
    
  
    
    
    01Чем git restore файл отличается от git restore --staged файл?
    Первая команда перезаписывает файл в рабочей папке, и правки теряются необратимо. Вторая перезаписывает только индекс, а правки в файле остаются.
    
    
    02Ты закоммитил, но не запушил, и хочешь исправить сообщение. Какая команда?
    git commit --amend -m "новое сообщение".
    
    
    03Что такое ветка физически?
    Файл в .git/refs/heads/, в котором записан хэш одного коммита.
    
    
    04Что делает git reset --soft HEAD~2 и где окажутся изменения?
    Переносит ветку на два коммита назад, не трогая индекс и рабочую папку. Изменения окажутся в индексе, готовые к новому коммиту.
    
    
    05Какой режим reset используется по умолчанию?
    --mixed: ветка и индекс сбрасываются, рабочая папка остаётся как была.
    
    
    06Почему после push нужен revert, а не reset?
    У других людей есть эти коммиты. Переписывание истории приведёт к расхождению, force push и возможной потере чужих коммитов. revert только добавляет новый коммит.
    
    
    07Чем HEAD~1 отличается от HEAD@{1}?
    HEAD~1 — родительский коммит. HEAD@{1} — где был HEAD до последнего действия, по журналу reflog.
    
    
    08Ты сделал git stash, переключил ветку, а новый файл остался в папке. Почему?
    Untracked-файлы без флага -u не прячутся.
    
    
    09Чем pop отличается от apply?
    pop = apply + drop.
    
    
    10git stash pop выдал конфликт. Что стало с записью в списке?
    Она осталась. После разрешения конфликта удали её сам через git stash drop.
    
    
    11Ты сделал git reset --hard и потерял незакоммиченные правки. Поможет ли reflog?
    Нет. reflog знает только о коммитах.
    
    
    12Ты удалил ветку через git branch -D. Как её вернуть?
    Возьми хэш из сообщения Deleted branch … (was хэш) или найди его в reflog. Затем git branch имя хэш.
    
    
    13Что делает git clean -n и почему его запускают первым?
    Показывает, что будет удалено, ничего не удаляя. clean -f необратим.
    
    
    14Коммит, сделанный пять коммитов назад, уже на сервере и оказался плохим. Как его отменить?
    git revert <хэш>.
    
    
    15Как склеить 3 последних (не запушенных) коммита в один?
    git reset --soft HEAD~3, затем git commit -m "…".

    Всё главное в одном месте. Её можно распечатать отдельно от конспекта.

    Что есть в Git
    
      
    
        
    Рабочая папка
    файлы на диске
    
        
    Индекс
    черновик следующего коммита
    
        
    Коммиты
    неизменяемые снимки
    
        
    Ветка
    файл с хэшем коммита
    
        
    HEAD
    файл с именем текущей ветки
    
      
    
    
    

    
    
      
    Правила
    
      
      
        
    • Паника: git status и читай подсказки в скобках.
      • 
        
    • Направление: вперёд — add и commit, назад — restore и reset.
      • 
        
    • reSet — для Себя, reVert — для Всех.
      • 
        
    • Страховка перед рискованной командой: git branch backup или git stash.
      • 
      
    
    
    

    
    
      
    Команды
    
      
      
        
    •  restore файл — индекс → рабочая папка
      • 
        
    •  restore --staged файл — коммит → индекс
      • 
        
    •  commit --amend — новый коммит вместо последнего
      • 
        
    •  reset --soft / --mixed / --hard — меняют 1, 2 и 3 места (ветку, индекс, рабочую папку)
      • 
        
    •  revert — новый коммит с обратными изменениями
      • 
        
    •  stash -u -m "…" — спрятать, stash pop — вернуть; pop = apply + drop
      • 
        
    •  clean — удаляет untracked, всегда сначала -n
      • 
        
    •  reflog — журнал перемещений HEAD; HEAD@{n} — где я был n действий назад
      • 
        
    •  --abort — выход из merge и rebase
      • 
        
    •  archive — zip с файлами коммита
